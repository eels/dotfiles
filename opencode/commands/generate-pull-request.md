Your job is to analyze the changes on this branch and generate a clear, structured pull request title and description that helps reviewers understand what changed, why, and how to verify it.

Before generating anything, analyze the project to infer test commands, build tools, and run instructions from configuration files and project documentation (e.g. `*.md` files). Use this information to produce concrete, actionable testing steps.

Principles:

- **Accuracy** — describe what actually changed; never fabricate or speculate.
- **Clarity** — reviewers should immediately understand scope and impact.
- **Completeness** — cover motivation, key changes, and testing steps.
- **Conciseness** — the description must never exceed 4,000 characters.

Workflow:

1. Identify the base branch from remote configuration or branch naming conventions.
2. Analyze the diff against the base branch using `git log` and `git diff`.
3. Infer project test commands and build tools from configuration files (e.g. `package.json`, `Makefile`, `justfile`, `Cargo.toml`) and project documentation (e.g. `*.md` files).
4. Categorise the change: feature, fix, refactor, chore, docs, test, or build.
5. Generate a PR title in conventional commits format (`type(scope): description`), imperative mood, no trailing period.
6. Generate a PR description following the Description Sections below, in order.
7. Measure the description length. If it exceeds 4,000 characters, trim the Summary section first; preserve Changes and Steps to Test.

Description Sections:

**Summary** — one-paragraph overview of what this PR does and why.
**Changes** — bullet list of key modifications, grouped logically by area.
**Steps to Test** — numbered instructions with concrete commands inferred from project tooling and documentation.

Rules:

- Never fabricate changes or speculate about intent.
- Never include AI attribution or "generated by" notes.
- Never exceed 4,000 characters for the description.
- Always base content on actual diff and commit history.
- Always include actionable testing steps with concrete commands.
- Always use imperative mood for the title; keep it under 72 characters.
- Default to conventional commits format for the title.

Priorities (first match wins):

1. If the diff is empty → report no changes to describe.
2. If the description exceeds 4,000 characters → trim the Summary section first.
3. If change type is ambiguous → default to `chore` and note the uncertainty.

Validation:

- Title accurately reflects the diff and follows conventional commits format.
- Description is grounded in actual changes, not speculation.
- Description does not exceed 4,000 characters.
- Testing steps are concrete, sequential, and use project-specific commands.
- No AI attribution or "generated by" language is present.

When complete, provide a final summary including:

- Proposed PR title.
- Description preview (or truncated notice if character limit was reached).
- Change type classification.
- Character count of the description.
- Base branch identified.
- Any assumptions made about intent or scope.
