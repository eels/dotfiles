Your job is to squash-merge the current feature branch into main, generating a commit message that matches the repository's existing commit convention.

Workflow:

1. Run `git status --short` to verify the working tree is clean — if uncommitted changes exist, stop and report.
2. Run `git branch --show-current` to identify the current branch — if already on main, stop and report.
3. Auto-detect the main branch: check for `main` then `master` locally; if neither exists, check `git branch -r` for `origin/main` or `origin/master`. If no main branch can be determined, ask the user.
4. Run `git fetch origin` to ensure remote tracking references are current.
5. Run `git log --oneline main..HEAD` to confirm the feature branch has commits ahead of main — if empty, report nothing to merge.
6. Run `git log --oneline -20 main` to infer the repository's commit message convention (match format, style, scope pattern). Default to conventional commits (`type(scope): description`) if no convention is detected.
7. Switch to main: `git checkout main && git pull origin main`.
8. Squash merge: `git merge --squash <feature-branch>`.
9. If merge conflicts occur: attempt automatic resolution for non-overlapping changes. If the conflicts require human judgment or input, stop and escalate to the user with a clear description of the conflict.
10. Analyse all staged changes (`git diff --cached`) and generate a single squash-merge commit message following the inferred convention. Use the feature branch name and change summary to inform the message.
11. Commit the squashed changes using `git commit -m "<message>"`. Never add AI attribution.
12. Switch back to the feature branch: `git checkout <feature-branch>`.
13. Report the merge commit message, the branch switched to, and whether the merge succeeded.

Principles:

- **Convention matching** — infer the repo's commit style from recent `git log` output and match it.
- **Safe merge** — verify clean state before merging, handle conflicts responsibly.
- **No push** — never push main or the feature branch after merging.
- **No attribution** — never add AI-generated credit to the commit message.

Rules:

- Never push after merging.
- Never commit outside the squash merge (this is the only commit in the workflow).
- Never add AI attribution or "generated by" notes.
- Always verify the working tree is clean before merging.
- Always auto-detect the main branch — never hardcode `main`.
- Always infer the commit message convention from `git log` — default to conventional commits if none exists.
- Always switch back to the feature branch after merging.
- Attempt automatic conflict resolution only for non-overlapping changes. Escalate to the user when human judgment is required.

Priorities (first match wins):

1. If the working tree is not clean → stop and report uncommitted changes.
2. If already on main → stop and report.
3. If no main branch can be detected → ask the user.
4. If the feature branch has no commits ahead of main → report nothing to merge.
5. If merge conflicts are non-overlapping → attempt automatic resolution.
6. If merge conflicts require human judgment → stop and escalate to the user.
7. If the inferred commit convention is ambiguous → default to conventional commits and note the assumption.

Validation:

- Confirm the working tree was clean before merging.
- Confirm the squash merge commit was created successfully on main.
- Confirm the commit message matches the inferred convention.
- Confirm the user was switched back to the feature branch.
- Confirm no push occurred.

When complete:
- Report outcome briefly (1-3 lines) unless issues occurred.
- Include, where relevant: the squash-merge commit message, the branch you switched back to, and whether the merge succeeded.
- If blockers, revisions, or risks existed, explain them.
- Only generate a full summary if the user explicitly asks.
